## Quick wins
- **Оновлення axios**: Запустіть \
pm update axios\ для закриття знайденої вразливості (займає < 15 хвилин).
- **Redis Rate Limiter**: Замініть \MemoryStore\ на \RedisStore\ (пакет \ate-limit-redis\ вже є у \package.json\, потрібно лише використати).

## Ризики
- **Брутфорс API**: Через відсутність розподіленого Rate Limiter на Vercel (інстанси без стану) зловмисники можуть обійти ліміти та спамити зовнішні API або сховище.

## Гіпотези до перевірки
- **Гіпотеза 4 (Брутфорс API)**: Потрібно перевірити поведінку \express-rate-limit\ у Vercel. Якщо Vercel Edge Cache не бере це на себе, Rate Limit не працює коректно.
- **Гіпотеза 5 (Витрати на Vercel)**: Синхронні виклики та довгі таймаути до зовнішніх API можуть перевищувати ліміти безкоштовного тарифу Vercel.

## Технічний борг
- Відсутність системи модульного тестування.
- Жорстке зв'язування HTTP-відповідей (req/res) з бізнес-логікою. Неможливо викликати функцію збереження ключа без створення HTTP запиту.
- Відсутність типізації (TypeScript не використовується).

## Roadmap
1. **Перше**: Виправити вразливості безпеки (npm audit) та налаштувати Redis Rate Limiter.
2. **Друге**: Розбити \server.js\ на контролери і роути, щоб покращити читабельність.
3. **Третє**: Налаштувати тестовий фреймворк та написати тести для критичних API.

## Відкриті питання
- **Статус Vercel Edge**: Незрозуміло, чи Vercel вже використовує власний WAF / Rate Limiter перед цим додатком (потребує перевірки дашборду Vercel користувачем).
